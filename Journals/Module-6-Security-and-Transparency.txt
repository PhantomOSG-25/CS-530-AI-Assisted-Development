Security and Transparency Risks in AI Systems
As AI becomes more common in software development and other high-impact areas, I think the biggest mistake is treating speed as proof of quality. AI can help a person work faster, but it can also produce an answer that looks convincing and is still wrong. For me, responsible use comes down to verification, security, transparency, and keeping a human responsible for the final decision.
Security and Transparency Risks
AI can affect decision making when people trust its recommendations more than they should. If the data behind a system is incomplete, biased, outdated, or manipulated, the output can lead a person in the wrong direction. That matters even more in healthcare, finance, employment, insurance, or cybersecurity, where a bad recommendation can have real consequences. Data integrity is part of the same problem. An AI system cannot reliably make good decisions from bad information. NIST recommends managing generative AI risks throughout the system lifecycle rather than treating trustworthiness as a one-time check (Autio et al., 2024). I think that is important because AI should help people make educated decisions, not make those decisions for them.
Vulnerabilities and Ethical Challenges
Code-generating AI creates another risk because code can run and still be wrong or insecure. In an earlier class activity, GitHub Copilot told me code with a syntax problem was valid even though Python and VS Code were showing an error. I had to challenge the answer before Copilot corrected itself. That experience made the risk very real to me. AI can also suggest outdated dependencies, weak input validation, or insecure coding patterns. Fu et al. (2025) found security weaknesses in AI-generated code taken from real GitHub projects, which backs up my concern that working code still has to be checked before it is trusted. The ethical issue is not simply whether AI is good or bad. It is whether the developer verifies the result and accepts responsibility for the code.
Risk Mitigation Strategies
I would treat AI-generated code the same way I would treat code from an unfamiliar source: review it before trusting it. Developers should test the code, review dependencies, scan for vulnerabilities, verify inputs and outputs, and keep software updated. These steps reduce the risk of cyberattacks, but they also help catch ordinary mistakes before they become security problems. Data breaches require another layer of protection. I would never put passwords, API keys, customer data, trade secrets, or other confidential information into an AI prompt unless the organization had specifically approved the system for that information.
Algorithmic bias also needs active testing. A system should be tested with different data and monitored for patterns that unfairly affect certain users. Adversarial manipulation is another concern because someone may intentionally provide inputs designed to confuse a model, reveal information, or change its behavior. Limiting permissions, validating inputs, monitoring unusual activity, and requiring human review for high-risk actions can reduce that risk. GitHub's guidance for responsible Copilot adoption also emphasizes using AI alongside established security practices instead of treating the tool as a replacement for them (McKinley, 2024).
Role of Transparency
I do not think transparency means publishing every technical detail or trade secret. Some information should remain private for security and competitive reasons. However, people should know what an AI system is being used for, what its limitations are, and who is accountable for the result. Explainability matters most when the consequences are serious. A person should be able to question an AI-assisted decision instead of being told that the system decided and nothing can be done.
Human oversight also has to be real. A reviewer needs enough information and training to recognize problems, and that person needs the authority to reject, stop, or escalate an AI decision without being punished for slowing down the process. If someone can technically override an AI system but is pressured not to because of deadlines or productivity goals, I do not consider that genuine oversight. Transparency helps build public trust because it gives people a way to understand the system and hold someone accountable.
Responsibilities of Different Entities
Responsibility is shared among governments, developers, and organizations, but shared responsibility cannot become “that is not my job.” Governments should establish baseline standards for privacy, safety, transparency, and high-risk uses of AI. Those rules also need consequences because rules without consequences are mostly suggestions. Developers are responsible for testing, documenting, securing, and verifying what they build, including code generated with AI. Using an AI assistant does not transfer that responsibility to the AI company.
Organizations are responsible for deciding which tools employees may use, what data may be shared with them, what reviews are required, and how deployed systems are monitored. They also need to give reviewers enough authority to act when they find a problem. In my view, AI is most useful when it helps people work and think more effectively while humans remain responsible for quality and safety. Quality should never be pushed aside simply to produce more work faster.
